# 安全边界

## 多用户数据隔离

当前版本采用应用层隔离，不是敌意多租户沙箱。

已隔离：

- 业务数据按 `user_id` 过滤
- 每个用户独立 workspace：`/data/workspace/<user_id>`
- 每个用户独立项目目录：`/data/workspace/<user_id>/projects`
- 每个用户独立钉钉配置和 token：`/data/workspace/<user_id>/dingtalk`
- 管理员只能管理账号和系统配置，不能查看其他用户业务数据
- 管理员的任务、指标等接口只返回自己的数据
- 普通用户不能创建或修改 stdio MCP
- 普通用户不能调用 root shell
- 公开注册默认关闭，只有空库的第一个账号可自助创建
- 管理员通过「用户管理」创建后续账号
- refresh token 会校验用户是否存在且未禁用
- 管理端删除用户会同步清理 pgvector `embeddings`
- 访问日志不记录 query string，日志格式化器会脱敏 token

## L0 限制

Coding Agent 的命令仍以共享的 `agent` 用户执行。

代码层会限制项目路径在当前用户目录内，但这**不是文件系统级隔离**。如果用户能够诱导 Coding Agent 执行恶意命令，理论上可以通过绝对路径读取其他用户的项目文件。

因此当前版本适用于：

- 内部可信用户
- 需要个人工作空间隔离，但不需要防范恶意租户的场景

如果未来需要敌意隔离，需要引入：

- 每用户独立执行身份，或
- mount namespace / bubblewrap，或
- 每用户独立容器

## 用户删除

管理员删除用户时：

1. 立即停用账号
2. 提交后台清理任务
3. 取消该用户的后台任务和运行中的 Bot/Coding Run
4. 断开 MCP Server 和钉钉登录会话
5. 删除 MinIO 中该用户的对象
6. 删除 `/data/workspace/<user_id>`
7. 删除数据库中的用户数据
8. 最后删除用户账号

删除需要管理员输入目标用户名确认。不能删除自己，也不能删除最后一个管理员。

MinIO 清理是 best-effort：如果对象存储暂时不可用，删除任务仍会继续，并在任务结果中记录错误。可通过按 `<user_id>/` 前缀重新清理遗留对象。
